EKS Platform — Design & Tradeoffs

Added: April 23, 2026 · Last updated: April 26, 2026

Built a production-style Kubernetes platform on AWS using EKS, Terraform, and Karpenter, focusing on secure workload isolation, efficient autoscaling, and repeatable infrastructure patterns.

Architecture Overview

The platform is centered around a managed EKS control plane, with worker nodes provisioned dynamically based on workload demand. All workloads run in private subnets — external traffic enters through an Application Load Balancer, and outbound traffic routes through a NAT gateway. Pod-level AWS access uses IRSA so each workload gets exactly the permissions it needs, nothing more.

  • VPC with public + private subnets across multiple AZs
  • EKS managed control plane
  • Worker nodes provisioned dynamically via Karpenter
  • IRSA for pod-level AWS access — no static credentials in the cluster
  • ALB ingress for external traffic via AWS Load Balancer Controller
  • CI/CD via GitHub Actions with OIDC → ECR → EKS
Treat the cluster as a platform — secure by default, scalable by design, and reproducible via Terraform.

Key Decisions & Tradeoffs

1 — Karpenter over Cluster Autoscaler

Problem: Cluster Autoscaler operates at the node group level, leading to inefficient bin-packing and slower scaling.

Cluster Autoscaler works at the node group level — it scales predefined groups up or down based on pending pods. In practice this means you're choosing instance types upfront, and the scaler picks from those options. Karpenter operates differently: it looks at pending pod requirements and provisions exactly the right instance for the workload — right size, right capacity type, right AZ — using EC2 APIs directly.

+ Better bin-packing and cost efficiency — right-sized nodes per workload, no over-provisioning
+ Faster scaling — provisions directly via EC2 API, no node group intermediary
- Higher setup complexity — NodePool, NodeClass, Pod Identity, and CRD ordering all have gotchas
- Less mature ecosystem — fewer community examples, docs cover the happy path only
Outcome: More efficient node utilization and faster recovery from capacity issues. Failed or undersized nodes were replaced automatically within ~90 seconds — no manual intervention needed.

2 — IRSA over static credentials

Problem: Static IAM credentials introduce security risks and operational overhead.

The alternative — mounting IAM credentials as Kubernetes Secrets — means a single leaked secret gives access to everything that role can do, across all pods. IRSA ties an IAM role to a specific Kubernetes service account in a specific namespace, using the cluster's OIDC provider as the trust anchor. AWS injects short-lived credentials into the pod automatically — no secrets stored in the cluster, no rotation needed.

+ Fine-grained, least-privilege access — each workload gets its own role scoped to exactly what it needs
+ No credential rotation — short-lived tokens injected automatically by AWS
- Complex setup — OIDC provider, trust policy, and service account annotation all have to align exactly
- Non-obvious debugging — a misconfigured trust policy gives a generic AccessDenied with no hint about which piece is wrong
Outcome: Secure, scalable AWS access model. Permissions are managed declaratively via Terraform without secret distribution — adding a new permission is a one-line policy change.

3 — Private subnets for worker nodes

Problem: Public nodes increase exposure and attack surface — nodes are directly reachable from the internet.

Worker nodes in private subnets are not reachable from the internet directly. All inbound traffic goes through the ALB in the public subnet, which terminates TLS and forwards to pods. Outbound traffic routes through a NAT gateway. The tradeoff is added networking complexity — NAT gateways cost money, and subnet tagging has to be done correctly for the ALB controller and Karpenter to discover the right subnets.

+ Reduced attack surface — nodes not directly reachable from the internet
+ Centralized ingress control — all external traffic funnels through the ALB
- NAT gateway cost — outbound traffic incurs NAT charges
- Increased networking complexity — subnet tagging, routing tables, and security groups all have to be right
Outcome: Stronger security posture with predictable ingress/egress patterns. The complexity is a one-time setup cost — once the VPC is provisioned correctly in Terraform it's just there.

4 — Vanilla Terraform vs Terragrunt for multi-region

Problem: Adding a DR region means duplicating every Terraform layer — same modules, different variable values per environment.

The current structure has environments/dev/ and environments/DR/ as near-identical copies. The modules are shared, but each environment has its own backend.tf, providers.tf, variables.tf, and main.tf calling the same modules with different inputs. Any change to a module interface — adding a variable, renaming a resource — requires updating both environments manually. Adding a third environment (staging, prod) multiplies the problem.

Terragrunt solves this by defining the layer structure once in a terragrunt.hcl and generating the per-environment boilerplate at runtime. Each environment becomes a thin config file: 

# environments/DR/general/terragrunt.hcl
include "root" { path = find_in_parent_folders() }

inputs = {
  region       = "us-west-2"
  cluster_name = "dr-eks-cluster"
  environment  = "dr"
}
+ No copy-paste — one module definition, many environments
+ DRY backend config — state bucket, key, and encryption defined once in root terragrunt.hcl
+ Dependency graph — dependency blocks replace manual output passing between layers
- Another tool in the chain — team needs to learn Terragrunt on top of Terraform
- Harder to debug — generated files add indirection, error messages point to generated code
- Overkill for two environments — the payoff grows with the number of environments
Decision: Kept vanilla Terraform for now — two environments doesn't justify the added tooling. Terragrunt becomes the right call at three or more environments, or when the copy-paste burden starts causing drift between environments.

Debugging Lessons

kubectl validation failing in CI after cluster recreate

Error: failed to download openapi: the server has asked for the client to provide credentials

This showed up after recreating the EKS cluster. The IAM role existed, OIDC was set up, aws eks update-kubeconfig was in the workflow — all looked right. What I missed is that EKS access entries are cluster-specific. When you destroy and recreate a cluster, they don't carry over. Since they weren't in Terraform, they were gone. Adding the access entry in Terraform fixed it and means it survives any future cluster recreate. 

resource "aws_eks_access_entry" "github_actions" {
  cluster_name  = module.eks.cluster_name
  principal_arn = "arn:aws:iam::<account-id>:role/github-actions-terraform"
  type          = "STANDARD"
}

resource "aws_eks_access_policy_association" "github_actions" {
  cluster_name  = module.eks.cluster_name
  principal_arn = "arn:aws:iam::<account-id>:role/github-actions-terraform"
  policy_arn    = "arn:aws:eks::aws:cluster-access-policy/AmazonEKSClusterAdminPolicy"
  access_scope { type = "cluster" }
}

IRSA — wiring up pod IAM access

For a pod to assume an IAM role, three things need to line up exactly: the EKS OIDC provider, an IAM role with a trust policy scoped to the specific namespace and service account, and the Kubernetes service account annotated with the role ARN. The part that got messy was the OIDC provider URL in the trust policy — it has to exactly match the cluster's issuer URL. Easy to get wrong if you're copying from an old role or a different cluster. 

# modules/irsa/main.tf
Condition = {
  StringEquals = {
    "${var.oidc_provider}:sub" = "system:serviceaccount:${var.namespace}:${var.service_account}"
    "${var.oidc_provider}:aud" = "sts.amazonaws.com"
  }
}
Lesson: IRSA failures are often trust-policy issues, not permission issues. Validate the OIDC URL, namespace, and service account name before debugging the IAM policy itself.

AWS Load Balancer Controller — missing IAM permission

Error: AccessDenied — elasticloadbalancing:DescribeListenerAttributes

The ALB wasn't getting provisioned. The IAM policy for the LBC was outdated — a newer version of LBC added a requirement for elasticloadbalancing:DescribeListenerAttributes that wasn't in the policy file. Added it and reapplied — ALB came up after that.

Lesson: LBC IAM policies drift over time as new versions add permissions. Pin the policy to the official upstream JSON for the specific LBC version you're running.

DynamoDB table already exists

Error: ResourceInUseException: Table already exists

The DynamoDB table was initially created through the AWS console. When Terraform later tried to manage it, it attempted to create a table that already existed. The fix was to import it into state rather than delete and recreate: 

terraform import module.dynamodb.aws_dynamodb_table.this app_events

A follow-on issue: DynamoDB has prevent_destroy = true, so terraform destroy on the cluster stack would fail every time. The fix was moving DynamoDB into its own isolated root module (environments/dev/datastores) with a separate state file — destroying the cluster no longer touches DynamoDB at all.

CoreDNS failing on fresh cluster apply — LBC webhook ordering

Error: AdmissionRequestDenied — no endpoints available for service "aws-load-balancer-webhook-service"

CoreDNS would fail every time a cluster was recreated. The LBC Helm chart installs a MutatingWebhookConfiguration before its own pod is ready, and CoreDNS gets caught by it on the way up. The fix was adding before_compute = true to the CoreDNS addon so it deploys before the node group — and before LBC has a chance to interfere. 

addons = {
  coredns = { most_recent = true, before_compute = true }
  vpc-cni = { most_recent = true, before_compute = true }
}

Networking — services unreachable after cluster recreate

Services were unreachable despite identical configuration after recreating the EKS cluster. The root cause was subnet tags (kubernetes.io/role/elb, kubernetes.io/role/internal-elb) not being applied correctly after recreation, preventing the ALB controller from discovering which subnets to place load balancers in.

Fix: explicitly enforced subnet tagging in Terraform and validated post-deploy.

Lesson: Networking is a first-class concern. Subnet tagging and routing must be treated as part of application correctness, not just infrastructure setup — validate them explicitly after every cluster recreate, not just when something stops working.

IAM — pods failing to access AWS services

Pods received AccessDenied despite correct IAM policies. The root cause was an OIDC provider URL mismatch (trailing slash) in the trust policy condition — the StringEquals check never matched, so AssumeRoleWithWebIdentity was silently rejected.

Fix: corrected the trust relationship to exactly match the issuer URL.

Lesson: IRSA failures are often trust-policy issues, not permission issues. Validate the identity assumptions — OIDC URL, namespace, service account name — before debugging the IAM policy itself.

What I'd Improve Next

  • Observability — introduce Prometheus, Grafana, and centralized logging early, not as an afterthought
  • Cost controls — Spot strategy, resource limits, and AWS Budget alerts
  • GitOps — adopt ArgoCD for declarative, auditable deployments instead of imperative kubectl apply
  • Multi-environment — extract reusable Terraform modules for clean dev/staging/prod separation
