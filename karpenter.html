Karpenter on EKS — Gotchas

Added: April 20, 2026 · Last updated: April 24, 2026

Things that weren't obvious when setting up Karpenter 1.11.1 on EKS with Terraform.

The Karpenter docs cover the happy path well but there are a few things that will silently break your setup and aren't easy to diagnose the first time. These are the ones I ran into.

1 — SecurityGroupsReady=False with no obvious cause

After deploying everything, the NodePool stayed in a not-ready state. Running kubectl describe nodepool general showed this in the events: 

NodeClassReady: False — SecurityGroupsReady=False

Karpenter discovers which security groups to use by looking for a tag: karpenter.sh/discovery = <cluster-name>. The subnets need this tag too, but that part is usually documented. The security group tag is not mentioned as clearly.

The fix is to add node_security_group_tags to your EKS Terraform module: 

node_security_group_tags = {
  "karpenter.sh/discovery" = var.cluster_name
}
Gotcha: Verify the tag actually exists after applying — don't assume it was set. 
aws ec2 describe-security-groups \
  --filters "Name=tag-key,Values=karpenter.sh/discovery" \
  --query 'SecurityGroups[*].{ID:GroupId,Tags:Tags}' \
  --region us-east-2
If it returns [], the tag isn't there — check that your apply completed cleanly.

2 — exec format error on new nodes

Pods were scheduled on a new Karpenter-provisioned node but immediately failed with: 

exec ./main: exec format error

Karpenter picks the cheapest instance that fits the pod's resource request. In us-east-2, that's often a Graviton (ARM64) instance like t4g.small. If your container image was built for amd64, it won't run on ARM — and the only indication is this error in the pod logs.

Fix: add an architecture requirement to your NodePool: 

requirements = [
  {
    key      = "kubernetes.io/arch"
    operator = "In"
    values   = ["amd64"]
  }
]
Alternatively, build a multi-arch image using docker buildx --platform linux/amd64,linux/arm64. That lets Karpenter freely choose Graviton instances which are cheaper for the same workload.

3 — Spot nodes were never used

Even with a spot NodePool configured, all nodes provisioned were on-demand. No errors or warnings anywhere. The reason is that the spot NodePool has a NoSchedule taint — pods without a matching toleration are simply ignored by that pool and fall through to the on-demand pool. Karpenter doesn't surface this anywhere, it just silently picks on-demand.

4 — Karpenter uses Pod Identity, not IRSA

Most pod-level IAM access in this project uses IRSA (IAM Roles for Service Accounts), which requires wiring up an OIDC trust policy manually. Karpenter uses the newer EKS Pod Identity mechanism instead — AWS handles the credential injection automatically once the eks-pod-identity-agent addon is running and create_pod_identity_association = true is set in the Karpenter module. 

module "karpenter" {
  source  = "terraform-aws-modules/eks/aws//modules/karpenter"
  version = "~> 21.0"

  cluster_name                    = var.cluster_name
  create_pod_identity_association = true
  namespace                       = "karpenter"
  ...
}
Gotcha: Pod Identity requires the eks-pod-identity-agent addon to be installed on the cluster. Without it, Karpenter pods can't assume their IAM role and will fail to start — with no obvious error pointing at the addon. 
addons = {
  eks-pod-identity-agent = { most_recent = true }
}

5 — Karpenter lives in a separate Terraform root

The NodeClass and NodePool manifests depend on Karpenter's CRDs being registered in the cluster. Those CRDs only exist after the Karpenter Helm chart has been deployed. This means you can't put Karpenter in the same root module as the EKS cluster — terraform plan will fail trying to resolve CRDs that don't exist yet.

The fix is a separate root module (environments/dev/addons) with its own state file that applies after the cluster is up. The deploy order is:

  1. environments/dev/general — VPC, EKS cluster, LBC, IRSA
  2. environments/dev/addons — Karpenter Helm + NodeClass + NodePool
This is the same reason DynamoDB lives in environments/dev/datastores — isolating things that have different lifecycle requirements from the main cluster stack prevents terraform destroy from being blocked by resources you didn't intend to touch.

6 — Topology spread constraints produce bad AZ spread during rolling updates

With topologySpreadConstraints set to spread pods across AZs (maxSkew: 1, whenUnsatisfiable: DoNotSchedule), a rolling update still produced a 4+1 distribution across 2 AZs instead of the expected 3+2. Restarting the rollout reproduced the same result.

The cause: the scheduler counts all pods matching the labelSelector when evaluating the spread — including old pods from the previous replicaset that are still terminating. As new pods are scheduled against a mixed count of old+new pods, the spread decisions are skewed. By the time old pods finish terminating, the final distribution is already locked in and violates the intended balance.

Gotcha: whenUnsatisfiable: DoNotSchedule only prevents making a violation worse at the moment of scheduling. It does not evict already-running pods to rebalance after the fact. A bad spread caused by a rolling update will persist until pods are rescheduled again.

Fix: add matchLabelKeys with pod-template-hash. This tells the scheduler to scope the spread calculation to pods from the current replicaset only — old terminating pods become invisible to the constraint. 

topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule
    matchLabelKeys:
      - pod-template-hash
    labelSelector:
      matchLabels:
        app: go-app

pod-template-hash is automatically added by Kubernetes to every pod in a replicaset. Each rollout gets a unique hash, so the new pods evaluate spread only against each other — producing a clean 3+2 distribution from the start.

matchLabelKeys is GA in Kubernetes 1.29+. EKS 1.31 supports it without any feature gates.
