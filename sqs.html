SQS, ESO & Config Management

Added: April 23, 2026

Moving from direct DynamoDB writes to an event-driven SQS pipeline, with External Secrets Operator handling config injection.

I started with the Go app writing directly to DynamoDB on a ticker. Next step was to introduce SQS as the messaging layer — the producer publishes events to a queue, and a separate consumer goroutine reads them and writes to DynamoDB. Config values (queue URL, table name) are no longer baked into the deployment via GitHub Actions secrets — they live in SSM Parameter Store and get injected into the pod via ESO.

1 — Terraform layer restructuring

Before adding SQS, the environments/dev/general root module had grown to include VPC, EKS, LBC, IRSA roles, IAM policies, access entries, and a DynamoDB data source — all in one place. Adding messaging resources on top of that would have made it worse.

The fix was to split general into purpose-specific layers, each with its own S3 state file: 

environments/dev/
  general/      # VPC, EKS, LBC, EKS access entries
  datastores/   # DynamoDB — prevent_destroy, never touched by cluster ops
  messaging/    # SQS queues, DLQs
  addons/       # Karpenter, ESO, Reloader
  permissions/  # IRSA roles + all app IAM policies

The ordering matters. permissions reads the EKS OIDC provider via a data source, so it has to run after general. addons installs ESO and annotates its service account with an IRSA role ARN from permissions, so it runs last in the Helm layer. The Makefile deploy target encodes this: 

make deploy  # general → permissions → addons → messaging
Why separate state files? Blast radius. A botched terraform destroy on messaging can't touch the EKS cluster. An apply on permissions doesn't refresh DynamoDB state. Each layer is independently plannable and destroyable.

2 — SQS module with for_each queues

Rather than hardcoding a single queue resource, the SQS module takes a map of queues and uses for_each to create a queue + DLQ pair for each entry. Adding a new queue means one line in terraform.tfvars — no module changes, no IAM changes. 

# messaging/terraform.tfvars
queues = {
  app-events = {}
  another-queue = { visibility_timeout = 60 }
}

The IRSA policy in permissions uses a wildcard ARN to cover all queues matching the prefix — so it also never needs to change when a new queue is added: 

Resource = "arn:aws:sqs:us-east-2:<account>:dev-*"

3 — SSM + ESO + Reloader for config injection

The old approach was passing DYNAMODB_TABLE and SQS_QUEUE_URL as GitHub Actions secrets, substituted into the deployment manifest via sed at deploy time. It worked but had two problems: config lived in GitHub secrets instead of alongside the infrastructure, and changing a queue URL required a full redeploy.

The new flow:

  1. Terraform writes config values to SSM Parameter Store after creating each resource
  2. ESO (External Secrets Operator) polls SSM every minute and syncs values into a Kubernetes Secret (go-app-config)
  3. The pod reads the secret via envFrom: secretRef
  4. Reloader watches the secret — when ESO updates it, Reloader triggers a rolling restart
# external-secret.yaml
spec:
  refreshInterval: 1m
  data:
    - secretKey: DYNAMODB_TABLE
      remoteRef:
        key: /dev/app/dynamodb/table-name
    - secretKey: SQS_QUEUE_URL
      remoteRef:
        key: /dev/app/sqs/app-events-url
# deployment.yaml
envFrom:
  - secretRef:
      name: go-app-config
annotations:
  secret.reloader.stakater.com/reload: "go-app-config"
Gotcha: pod starts before ESO syncs the secret. The first time this was deployed, the pod came up and started the SQS ticker — but SQS_QUEUE_URL was empty because the go-app-config secret didn't exist yet. ESO hadn't finished its first sync. The ticker fired but the publish silently failed because SendMessage was called with an empty queue URL. The fix was to delete the pod so it restarted after the secret existed. Going forward, Reloader handles this — when ESO creates or updates the secret, it triggers a restart automatically.
ESO needs its own IRSA role — separate from the app's role. ESO's service account (external-secrets in the external-secrets namespace) needs ssm:GetParameter on the parameter path. The app's IRSA role also gets ssm:GetParameter as a fallback, but in practice the app reads config from env vars injected by ESO, not from SSM directly.

4 — Helm provider v3 syntax change

Error: Blocks of type "set" are not expected here. Did you mean to define argument "set"?

The Helm Terraform provider v3 changed set from a block to an argument. The old syntax: 

# provider v2 — block syntax
resource "helm_release" "external_secrets" {
  set {
    name  = "serviceAccount.annotations.eks\\.amazonaws\\.com/role-arn"
    value = data.aws_iam_role.eso.arn
  }
}

The new syntax in provider v3:

# provider v3 — attribute syntax
resource "helm_release" "external_secrets" {
  set = [
    {
      name  = "serviceAccount.annotations.eks\\.amazonaws\\.com/role-arn"
      value = data.aws_iam_role.eso.arn
    }
  ]
}

5 — Karpenter picking undersized nodes

After adding ESO and Reloader, the cluster started hitting memory pressure. Pods were being evicted with The node was low on resource: memory. Threshold quantity: 100Mi, available: 50804Ki.

Karpenter had provisioned t3a.nano instances — 512MB RAM — because the NodePool had no instance size constraint and nano is the cheapest option that fits a pod's CPU/memory request. With system pods, Karpenter, ESO, and Reloader all competing for memory, nano was nowhere near enough.

The fix was adding instance size requirements to the NodePool: 

requirements = [
  {
    key      = "karpenter.k8s.aws/instance-category"
    operator = "In"
    values   = ["t"]
  },
  {
    key      = "karpenter.k8s.aws/instance-size"
    operator = "In"
    values   = ["small", "medium", "large"]
  }
]
Gotcha: Karpenter doesn't warn you that a node is undersized for the workload — it just provisions whatever fits the resource requests. If your pods don't have accurate memory requests set, Karpenter will happily provision a nano and let the kubelet evict pods when actual usage exceeds available memory.

6 — helm_release cannot re-use a name that is still in use

Error: installation failed — cannot re-use a name that is still in use

This came up during the first make apply RESOURCE=addons after adding ESO. The first pass of the two-phase Karpenter apply had already installed ESO via Helm before Terraform tried to manage it. Terraform didn't have it in state, so it tried to create it — but Helm already had a release by that name.

The fix is to import the existing Helm release into Terraform state: 

terraform -chdir=environments/dev/addons import \
  helm_release.external_secrets \
  external-secrets/external-secrets
